# Phase 3: Analysis, Dashboard and Bulk Upload (MVP)

## Scope and prerequisite

- Implemented: four-table schema, Alembic migration, Phase 2 normalization, ingestion (`ingest_rows`) and `seed.py`. Phase 3 reuses them and changes neither Phase 2 nor the schema.
- Each reading stores `fridge_id`, so the unit of analysis is a **series**: readings for one `(logger_id, fridge_id)`, ordered by time. A logger that moved becomes two series, and nothing is assumed across the move.
- The dashboard is **fridge-first**: Summer asks about fridges, not loggers, so there is one card per physical fridge (branch + fridge name). Analysis stays per series. A fridge with several loggers over time shows each logger's history separately and never merges them into one trend.
- **Phase 2 gaps handled in Phase 3** (Phase 2 is not modified; see "Phase 2 behaviour that Phase 3 must handle"): a fridge-only difference is not reported as a conflict, there is no per-reading fridge resolution, no column validation for `Time`/`Temp` files, and no reporting-week or coverage concept.
- **Retrospective, not real time:** the dashboard answers "what happened to each fridge during the selected week", using every reading in that week. It never claims the current state of a fridge and never treats unobserved time as safe.

## Two workflows

- **Development / demo:** `python -m app.seed` loads the 16-row sample, as today. It is for demos only and is not used in a real environment.
- **Summer's real workflow**, always through the web UI with no file paths:
  1. **Initial Setup / Historical Import (one time):** her existing combined file (Logger, Branch, Fridge, Time, Temp; about 3,000 rows) populates loggers, fridges, historical assignments and readings.
  2. **Weekly Upload (every week):** several new files that may hold only `Time` and `Temp`. Mappings come from the database, so the combined file is never needed again. A genuinely new logger is the exception and is registered in the review (see Weekly Upload).

Both use the same Phase 2 ingestion, normalization and deduplication.

## Initial Setup: historical import (one time)

- **Input:** one combined `.xlsx` (up to 5 MB), picked in the browser. It is `mode=historical` of the same `review` and `import` endpoints, using the Phase 2 combined-format reader.
- **Review (dry run, nothing saved):** rows read, the loggers, fridges and assignments that would be created (names listed, so spelling variants such as "Walk-in" vs "Walkin" can be spotted), readings to insert, the unit applied to each new logger (below), duplicates, conflicts (including fridge conflicts, see "Phase 2 behaviour that Phase 3 must handle"), NULL (`ERR`) readings, and rejected rows with row numbers and reasons.
- **Units are predefined only where there is evidence, applied automatically, shown and overridable.** The file has no unit column. In `upload.py`, `HISTORICAL_LOGGER_UNITS = {"TL-0231": "F"}` records the one known fact: TL-0231, the old Haifa logger, is Fahrenheit. `HISTORICAL_DEFAULT_UNIT = "C"` applies automatically **only to a new logger whose branch is not Haifa**, since nothing suggests otherwise for those. They are passed to ingestion explicitly as `logger_units` (the ingestion's own default is never relied on). The review lists every such logger with its applied unit; one control per logger lets Summer override it before importing (existing loggers show their stored unit, read-only).
- **A new Haifa logger other than TL-0231 is not assumed to be Celsius.** Haifa is the one branch with a known Fahrenheit logger, so a different unmapped unit there is plausible and the `C` default does not apply to it. The review lists it with **no unit pre-filled** and a required C/F choice; Import stays disabled until every such logger has one. This is a one-time verification per logger code: once chosen, it is stored on `loggers.unit` (same as any other logger) and never asked again, including in later historical or weekly imports. Everywhere else, "no branch rule applies" still holds: a new Haifa logger is not assumed Fahrenheit either, just not defaulted at all.
- **No inference, no spread.** Units are never inferred from temperature values. The `C` default for non-Haifa loggers is **not** a rule for loggers added later: a new logger registered in Weekly Upload (Haifa or not) always gets an explicitly confirmed unit, exactly like an unmapped Haifa logger here. `seed.py` keeps its own `SAMPLE_LOGGER_UNITS` (unchanged), and a test checks that it agrees with `HISTORICAL_LOGGER_UNITS` on TL-0231.
- **Historical assignments, no invented dates.** Each `(logger, fridge)` pair in the file becomes an **undated** assignment (the Phase 2 behaviour), and every reading keeps the fridge it was reported under. Moves that happened in the history have no dates and none are created. Consequence: a logger seen under several fridges has several undated assignments, so its weekly files stay unresolved until Summer records one move (its current fridge, with an effective date and time) in Weekly Upload.
- **Import:** valid rows are imported in one transaction committed once. Rejected rows are reported and not stored, so Summer fixes them in the Excel file and imports again (only the fixed rows are added). An unexpected error writes nothing.
- **Repeat imports are safe:** existing readings are never duplicated (unique on logger and time), and a different value, or a different fridge, at an existing key is reported as a conflict, with the first stored reading kept and never overwritten.
- **Result screen:** counts of loggers, fridges, assignments and readings created, duplicates, conflicts, NULL readings, and rejected rows (first 100 plus the total), then "Go to Weekly Upload" and "View dashboard".
- **Limits:** a logger or fridge name that was misspelled in the Excel file and imported cannot be edited or merged in the MVP, and a logger's unit cannot be changed after import. The review and its unit override exist so these are caught first. The seed is a demo command and should not be run in a real environment.

## Detection rules (`backend/app/analysis.py`)

Pure functions over `(measured_at, temperature_c or None, raw_value)`. Constants live at the top of the file, are passed in explicitly for tests, and are documented in `NOTES.md`.

| Constant | Value |
| --- | --- |
| `THRESHOLD_C` | 5.0 (excursion means strictly above) |
| `GAP_MIN` | 30 (more than 2 of the sample's 15-minute intervals) |
| `WARMING_MIN_READINGS` / `WARMING_MIN_RISE_C` / `WARMING_MAX_STEP_SHARE` | 4 / 1.0 / 0.5 |

- **Invalid readings** (`temperature_c` NULL, such as `ERR`) never supply a value and are listed as data-quality issues. They are **not skipped over**: the analysis walks the full time-ordered sequence, and an invalid reading **ends the current excursion or warming run** exactly like a gap, because the temperature at that moment is unknown. Without this, `7.0, ERR, 7.2` at 15-minute steps would look like one continuous excursion (the two valid readings are only 30 min apart, which is not a gap).
- **Gap:** more than `GAP_MIN` minutes between consecutive valid readings. Nothing is interpolated.
- **Excursion:** a run of consecutive readings (no invalid reading and no gap between them) all above 5 C. Reports start, end, peak, reading count, and `ended_by`, one of `recovered`, `gap`, `invalid_reading`, `end_of_period` or `end_of_data`. **The two "end" cases are kept distinct and neither is guessed as the other:** `end_of_period` means the run is still open at the last reading *within the selected week*, but the series has at least one later reading in the database (outside the week) — the run may have continued or recovered after the week boundary, and that is a fact to check in a later week, not an assumption. `end_of_data` means the run is still open at the series' actual last reading, with **no later reading anywhere in the database** — there is nothing to say whether or how it ended. A series with no reading after the run is always `end_of_data`, even when that happens to coincide with a week boundary; it is never mislabelled as `end_of_period`. Checking which applies looks only at whether a later reading exists, not at its value.
- **Duration:** first to last above-threshold reading, a **lower bound**. It never spans a gap or an invalid reading, and never extends to the next reading. One reading means duration 0, shown as "single reading"; `gap`, `invalid_reading`, `end_of_period` or `end_of_data` endings are shown as "at least".
- **Spike vs sustained:** a one-reading excursion that recovered is an `isolated_spike`. Two or more readings is `sustained`. A one-reading excursion ended by a gap, an invalid reading, the end of the period or the end of the data is "unconfirmed".
- **Gradual warming:** at least 4 consecutive valid readings with no gap or invalid reading between them, every step rising, total rise at least 1.0 C, and no single step more than half the total (the spike guard: `4.0, 4.1, 4.2, 9.4` is not warming). Independent of the threshold, so it can warn before 5 C.
- **Data-quality issues:** `invalid_reading` (time and raw value), `gap`, `single_valid_reading`.

**Golden results on the 16 sample rows, for the week of Monday 2026-09-14 (unit and API tests):**

| Series | Series findings | Fridge result for the week |
| --- | --- | --- |
| TL-0388 Rishon LeZion / Cream cakes | Sustained excursion 06:15 to 06:45, peak 7.1, 30 min, `end_of_data` (no later reading for this series at all, so it is not labelled `end_of_period`). Gradual warming 06:00 to 06:45, rise 2.5. | `excursion_observed` (low coverage noted) |
| TL-0417 Tel Aviv / Walk-in | Isolated spike at 06:15, peak 9.4, duration 0. No warming. | `excursion_observed` |
| TL-0417 Tel Aviv / Display 2 | Nothing above threshold, `single_valid_reading`, 0 observed minutes. | `insufficient_data` |
| TL-0512 Jerusalem / Dairy | No excursion. One gap of 135 min (06:15 to 08:30). | `insufficient_data` |
| TL-0231 Haifa / Dairy | No excursion. One `invalid_reading` (`ERR`). | `insufficient_data` |

No sample fridge reaches `MIN_COVERAGE` (at most about 45 minutes observed in a 168 hour week), so none may be reported as "no excursion observed". None of the sample series has a reading in any other week either, so every open run above is `end_of_data`, not `end_of_period`.

## Weekly retrospective report and data coverage (pure functions in `analysis.py`)

Monitoring is **retrospective, not real time**. Summer uploads weekly and asks what happened to each fridge **during a reporting week**, even if the temperature has since returned to normal. There is no "current status", no clock comparison and no `now`.

| Constant | Value |
| --- | --- |
| `WEEK_START_DAY` | Monday — **provisional**, pending Summer's confirmation (see open questions) |
| `MIN_COVERAGE` | 0.90 — **provisional**, pending Summer's confirmation (see open questions) |

Both constants are business assumptions, not derived facts, and both are called out in the open questions below and in `NOTES.md`. Changing either is a one-line config change, not a redesign, and every acceptance test using them names the constant rather than hard-coding 0.90 or Monday.

- **Coverage is an estimate, not proof of continuous monitoring.** A gap of up to `GAP_MIN` between two valid readings is treated as observed, because nothing closer in time was recorded; it is not evidence that the temperature stayed below 5 C for every second in between, only that no logged value says otherwise. "Observed" means "a reading exists close enough in time to assume nothing was missed by design", never "confirmed safe for that whole interval". The UI's coverage line and the `no_excursion_observed` wording make this an estimate from recorded samples, and the unobserved-period wording already says periods with no nearby reading are unknown, not safe; this phrasing is reused everywhere coverage is shown so no screen implies continuous proof.
- **Period:** every reading with `measured_at` in the selected week is analysed, using the rules above on that week's readings only. Weeks are Monday-based windows (provisional); no time zone handling. A run at the edge of the week is reported for its in-week readings; its `ended_by` is `end_of_period` or `end_of_data` per the rule above, and durations stay lower bounds.
- **Excursions stay visible:** every excursion strictly above 5 C in the week is listed with start, end, peak, duration wording and `ended_by`, **even when the temperature recovered**. Nothing is cleared by a later normal reading.
- **Maximum recorded temperature:** the highest valid `temperature_c` in the week, with its time, per series and per fridge. Invalid readings are never part of it.
- **Observed time and coverage:** within a series, a continuous run of valid readings (no gap, no invalid reading) counts as observed from its first to its last reading, and nothing else does. Coverage is observed minutes divided by the week's minutes. A single reading observes 0 minutes. For a fridge, the observed intervals of its series are **merged** (union, so a logger that moved mid-week or two overlapping loggers are not double counted), and this is only a time calculation: no detection rule ever runs across series.
- **Unobserved periods:** the week minus the observed intervals, listed when longer than `GAP_MIN` (the week start to the first valid reading, each gap, each invalid-reading break, the last valid reading to the week end). They are shown, never filled.
- **Fridge result for the week** (first match wins; the findings lists are always shown too):
  1. `excursion_observed`: at least one series has an excursion. Shown even when coverage is low, with the coverage note.
  2. `warming_observed`: no excursion, but at least one gradual-warming run.
  3. `insufficient_data`: none of the above and merged coverage is below `MIN_COVERAGE` (including no valid readings at all). It says "No excursion was observed in the recorded readings, but N of the week's hours were not observed", never "safe" or "OK".
  4. `no_excursion_observed`: none of the above and coverage is at least `MIN_COVERAGE`. Wording: "No excursion observed" with the coverage figure and any unobserved periods. It is a statement about the recorded readings only; unobserved periods are never described as safe.
- **Week selector and default:** the weeks offered are those that contain at least one reading, newest first. The default is the **latest week containing readings** (by the newest `measured_at` of any reading). A week still in progress is a full-week window, so it reads `insufficient_data` until enough of it is observed.
- **Demo data:** the 16-row sample all falls in the week of Monday 2026-09-14, so the dashboard and golden tests use that week without any clock.

## Weekly Upload design

**Problem:** dozens of logger files a week; a file may hold only `Time` and `Temp`. Nothing is required to identify the logger, and nothing is guessed. Fridge and unit mappings are read from the database (created by the historical import, recorded moves or a registered new logger). The weekly screen asks Summer to run Initial Setup first when no loggers exist yet.

**The database does not identify a file.** Saved mappings say which fridge a logger is in, not which logger a file belongs to. If neither an exact file-name match nor Summer's selection names the logger, the file stays in Needs attention, even when only one logger exists. Nothing is inferred from the file's contents.

**Flow:** pick many `.xlsx` files, then `review` (a dry run), fix what needs attention, then `import`, then per-file results. The browser keeps the `File` objects, so the server stores nothing between steps.

- **Files:** `.xlsx` only, first sheet, up to 100 files and 5 MB each. `Time` and `Temp` columns required (also `Timestamp`, `Temperature`; case-insensitive). A `Time`/`Temp`-only file is fully valid. Row cleaning is the Phase 2 normalization. **Optional `Logger`, `Branch` and `Fridge` columns are validated, never used to identify or resolve anything:** each non-blank value is compared (case-insensitively, after the Phase 2 name cleaning) with the logger resolved for the file and the fridge resolved for that reading. Any mismatch makes the file `needs_attention`, nothing from it is written, and the message lists the first mismatches ("row 14 says Walk-in, but TL-0417 resolves to Display 2 at that time"). Summer can then change the selected logger or record the missing move. This is Phase 3 code (the Phase 2 reader only checks the `Logger` column, row by row).
- **Logger:** detected from the **file name only**, when exactly one known logger code matches as a whole token, ignoring case (`TL-0512_2026-09-14.xlsx` yes; `XTL-05123.xlsx` and `TL-0512_TL-0417.xlsx` no). Otherwise Summer selects it in the review screen. Never inferred from temperatures, units, timestamps, the database or other data. Detection is a convenience, not a guarantee: detected loggers stay visible and changeable, and `source_file` is stored on every reading.
- **A genuinely new logger (an exception, not per-file setup):** in Needs attention, the logger dropdown has a "New logger" choice. Summer **types the code** (never prefilled or guessed from the file name), **confirms its unit** (a required C or F choice; the historical default does not apply), and **picks an existing fridge**, then presses Confirm. It is staged like a move and **nothing is saved until Import**. A code that already exists (case-insensitively) is refused with "select it from the list". At import, before the files, the logger is created in `loggers` and one **undated** `logger_assignments` row is created for the chosen fridge: no date is invented, and that row is the logger's last known mapping, so the file resolves under the single-undated-assignment rule below. If the staged logger's files do not import, the logger is still saved (like a move) and later files find it in the database. Known loggers never need this. Creating a new fridge is out of scope (the historical import creates fridges).
- **Fridge, resolved per reading by timestamp** from the logger's assignments plus any recorded moves. For a reading at time `t`:
  1. **From a dated move onward:** the assignment with the latest `assigned_from <= t` that is still open at `t` wins. A file spanning a known move is split automatically by timestamp, so Summer never splits the Excel file.
  2. **Before that (a move says nothing about earlier readings):** only a confirmed historical assignment may be used. That is a dated assignment that covers `t`, or, if the logger has **exactly one undated assignment**, that one as the **last known mapping** (not guaranteed to be current truth: an unreported move cannot be detected, see Limitations).
  3. **Otherwise** (no assignment, or several undated ones such as TL-0417's) the reading is **unresolved**. The previous fridge is never guessed, and a move's fridge is never applied backwards.
- **A file is imported only if every reading resolves.** Otherwise that file is `needs_attention` and nothing from it is written; the reason names the first unresolved time. Other files are never affected. For a file spanning an unresolved period the review says so in plain words, for example: "TL-0417 was in two fridges (Walk-in, Display 2) with no recorded dates, so readings before 17 Sep 06:00 cannot be assigned. Record each known move with its date and time (including the earlier one), then review again." The files stay in the batch; nothing is guessed.
- **Recording moves (optional):** logger, destination fridge, effective date and time. Saved as a dated row in `logger_assignments` (`assigned_from` set, `assigned_to` empty); earlier rows are untouched, and the date comes only from Summer. Moves are saved first at import (after any new loggers) and persist even if no file imports. They never re-attribute or rewrite readings already imported. A move resolves only the readings its effective time supports, from that time onward. To make earlier readings resolve, Summer records the earlier known move too.
- **Integrity checks before ingestion (Phase 3 code):** a reading whose `(logger, measured_at)` already exists, in the database or earlier in the same batch, but under a **different fridge** is a **conflict even when the temperature is identical**. It is reported (first stored reading wins) and never inserted or overwritten. Other readings of the file still import. See "Phase 2 behaviour that Phase 3 must handle".
- **Partial success:** each file is imported in its own committed transaction. An unresolved, invalid or failing file never blocks or rolls back another file. Re-importing is safe (duplicates are skipped by `(logger, measured_at)`).
- **Unresolved files are not stored.** There is no staging or upload table. They stay only on the review screen, where Summer can fix and re-import them. The UI says: "N files were not imported and are not saved on the server. Resolve them now or upload them again later. Leaving or reloading this page discards them." The page also asks for confirmation before it is left.

## Phase 2 behaviour that Phase 3 must handle (Phase 2 is not modified)

Checked against `backend/app/ingest.py`. `upload.py` adds the following around `ingest_rows` and does not change it:

- **Fridge-only differences are silent duplicates in Phase 2.** `_store_readings` keys on `(logger, measured_at)` and compares only the temperature, so the same logger and time with the same value under a different fridge is counted as a duplicate and the fridge difference is lost. A different value is a conflict, but its message has no fridge. **Phase 3:** before calling `ingest_rows`, `upload.py` compares each row's fridge identity (branch and name, case-insensitive) with the stored reading for that `(logger, measured_at)` and with earlier rows of the same batch. A mismatch is removed from the rows passed on and reported as a fridge conflict with row number, both fridges and the kept value. Rows with a different value and the same fridge still go through Phase 2's conflict report.
- **One fridge per file.** `read_xlsx_rows` takes a single explicit fridge. **Phase 3:** `upload.py` reads the file with the logger and any fridge from its assignments, parses each reading's time, resolves its fridge, and sets each row's branch and fridge name to the resolved fridge before `ingest_rows`. Resolved fridges always come from an existing assignment, so ingestion creates no new assignment in the weekly flow (tested).
- **Column validation, new-logger creation and fridge resolution** are Phase 3 only. Phase 2 creates loggers only as a side effect of ingesting rows, so the weekly new-logger registration creates the `loggers` and `logger_assignments` rows itself, with the existing models.
- **Units:** Phase 2 defaults a new logger to `C` when `logger_units` has no entry. Phase 3 always passes an explicit unit for TL-0231 and for a non-Haifa logger, and refuses to call ingestion at all for an unmapped Haifa logger until Summer supplies one, so that Phase 2 default is never used.
- **Invalid readings** are stored with NULL `temperature_c` and raw text kept (correct). Keeping them from joining separate runs is the analysis rule above, in Phase 3.
- **Dry run:** ingestion never commits, so `review` can run the real code and roll back.

## Endpoints (5)

- `GET /api/lookups`: loggers (id, code, unit) and fridges (id, branch, name) for the dropdowns.
- `GET /api/overview?week=YYYY-MM-DD`: the report for one reporting week. `week` is optional and any date selects its Monday-based week; omitted, it is the **latest week containing readings**. No clock or `now` is involved. The response has `weeks` (the Mondays that contain readings, newest first), `week` (start and end of the selected week), and `fridges`, **one entry per fridge** (`fridge_id`, branch, name): `result` (`excursion_observed`, `warming_observed`, `insufficient_data`, `no_excursion_observed`), `max_temperature_c` with its time and logger, `coverage` (observed minutes, share of the week, and the listed unobserved periods, from merged series intervals), counts of excursions (sustained and isolated spikes), warming runs, gaps and invalid readings, and a `series` list (one item per logger with readings in the week: `logger_id`, code, observed minutes, max, and its own counts). Analysis runs per series; the fridge entry only groups the findings. A fridge with no valid readings that week is `insufficient_data`. With no readings at all, `weeks` and `fridges` are empty and the UI points to Initial Setup.
- `GET /api/series/{logger_id}/{fridge_id}?week=YYYY-MM-DD`: the readings of that one series in the selected week (including invalid ones, with raw text) and all its findings: every excursion (kind, start, end, peak, duration, `ended_by`), warming runs, gaps, invalid readings, maximum, observed minutes and unobserved periods. `week` defaults to the same latest week. Fridge detail calls it once per item of the fridge's `series` list, so loggers are never merged. The series has no result badge of its own.
- `POST /api/uploads/review` and `POST /api/uploads/import` take the same multipart request, with a `mode` field. `weekly` (default): `files`, `selections` (JSON `{file_index: logger_id}`, or `"new:<CODE>"` for a staged new logger), `new_loggers` (JSON list of `{code, unit, fridge_id}`, unit required) and `moves` (JSON list of `{logger_id, fridge_id, effective_at}`). `historical`: exactly one `file`, plus `logger_units` (JSON `{logger_code: "C" | "F"}`), **required** for a new logger whose branch is Haifa and whose code is not TL-0231, and optional elsewhere as an override of the applied default. Import refuses, writing nothing, while any Haifa logger (other than TL-0231) in the file has no entry. They share one function, and `review` for `historical` returns each new logger with its applied or missing unit and source (`known`, `default`, `override` or `unresolved`). `review` runs it inside a transaction that is **rolled back**, so it reports exactly what import would do and writes nothing. `import` commits the new loggers and moves first, then each file separately.
- Per-file result: `status` (`ready`/`imported`, `needs_attention`, `invalid`, `failed`), detected or selected logger, fridges used, `inserted`, `duplicates` skipped, `conflicts` (same logger and time with a different value, first wins) and `fridge_conflicts` (same logger and time under a different fridge, even with the same value; first wins), `mapping_mismatches` (optional `Logger`/`Branch`/`Fridge` columns that disagree with the resolved mapping), `rejected` rows (number and reason), `invalid_values` stored as NULL, `unit_converted`, and a `message` when not imported.
- New backend dependency: `python-multipart`. Analysis runs on request from stored readings. **No new tables.**

## Frontend (React + TypeScript, mobile-first, no router, no chart library)

- **Dashboard (fridge-first, weekly):** a header with the selected week ("Week of 14 Sep 2026") and a **week selector** (the weeks that contain readings; the latest is selected on load, with previous and next controls). Below it, one card per physical fridge for that week: branch and fridge name, a result badge (`Excursion observed`, `Warming observed`, `Insufficient data`, `No excursion observed`), the **maximum recorded temperature** with its time, the counts (excursions with sustained and isolated spikes, warming runs, gaps, invalid readings), and a coverage line ("Observed 97% of the week" or "Observed 12% of the week: 148 h not observed"). Excursions are never hidden by a later recovery. Wording never says "safe" or "OK", and `No excursion observed` always sits next to the coverage line. Cards with excursions sort first, then warming, then insufficient data. One column on phones, a grid from about 640 px, tap targets of at least 44 px. With no readings the page points to Initial Setup. No "current status", ages or live indicators are shown anywhere.
- **Fridge detail (same selected week):** a section **per logger series** in time order (for example "TL-0417, until it moved" and "TL-0417, since the move"), never combined into one trend. Each section shows its maximum, an inline SVG line chart with the 5 C line (never drawn across a gap or an invalid reading, with unobserved periods marked), then lists of excursions (with the duration wording above and `ended_by`), warming runs, gaps with their length, and invalid readings with their raw text.
- **Navigation:** a simple tab bar (state-based, no router) with **Dashboard**, **Weekly Upload** and **Initial Setup (Historical Import)**. The two import screens are separate and each opens with one line saying what it is for ("One-time: load your existing combined file" and "Every week: upload new logger files").
- **Initial Setup screen:** pick one file, review summary with counts, the names to be created, each new logger with its applied unit and a small control to override it, **and a required C/F choice (nothing pre-filled) for any new Haifa logger other than TL-0231**, and the rejected rows list, then Import (disabled until every required choice is made) and the result screen described above. The flow stays upload, review, import, with that one required choice only when it applies. Rejected rows are fixed in the Excel file and imported again.
- **Weekly upload review** (calls `review` after picking files and after each change): a summary line, then **Needs attention** first (file, reason in plain words as above, logger dropdown with a "New logger" choice that opens the code, unit and fridge form), **Invalid** (file, reason, remove), and **Ready** collapsed with a count (file, logger and its source, fridge or fridges). ## Acceptance criteria

1. Constants are defined in one place, documented in `NOTES.md`, and results are deterministic. The golden table is reproduced in the unit test and through the API.
2. No duration crosses a gap or an invalid reading, and no value is interpolated. An `ERR` reading never joins two excursions or warming runs. The `4.0, 4.1, 4.2, 9.4` series is not warming, and the 9.4 C sample reading is an isolated spike.
3. Invalid readings, gaps, rejected rows and conflicts are visible in the UI with time and reason.
4. Up to 100 files upload in one batch, including `Time`/`Temp`-only files. A logger is auto-detected only from an exact, unambiguous file-name match, never from data or from the saved mappings, and the UI does not claim it is guaranteed. Detected loggers stay visible and editable, and any other file waits for Summer's selection.
5. The fridge is resolved per reading by timestamp: a known move splits a file automatically, readings before it use only a confirmed historical assignment (one undated assignment is the last known mapping), and an ambiguous fridge is never guessed or taken from the move. TL-0417 with two undated assignments leaves its earlier readings unresolved without blocking other files.
6. Review leads with files needing attention, and ready files need no per-file confirmation. Moves can be recorded before import, with no inferred dates.
7. Valid files import independently with a commit each. No unresolved, invalid or failing file blocks or rolls back another, and unresolved files are not stored, which the UI states.
8. Per-file results show imported rows, skipped duplicates, rejected rows, conflicts (value and fridge), and files requiring attention. Re-import inserts nothing. No new tables are added.
9. At 375 px width there is no horizontal scrolling and tap targets are usable (checked in the browser).
10. **Initial Setup:** Summer uploads her combined file (about 3,000 rows) through the UI with no file path, reviews the counts, and imports it. Loggers, fridges, undated assignments and readings are stored in PostgreSQL by the Phase 2 ingestion. TL-0231 is applied as Fahrenheit and a non-Haifa logger as Celsius, both automatically and shown in the review with an override available; a new Haifa logger other than TL-0231 is never defaulted and needs a one-time required C/F choice before Import, then its unit is stored and never asked again. No unit is inferred from values and no move date is invented, invalid rows and conflicts are reported, and importing the same file again adds nothing.
11. **Weekly Upload:** `Time`/`Temp`-only files use the mappings and units already in the database, so the combined file is never needed again. The filename detection, review, recorded moves, partial success and data-quality reporting behave as above.
12. Initial Setup and Weekly Upload are separate, clearly labelled screens. Unresolved mappings can be corrected in the review, and valid files never need individual confirmation.
13. **New logger:** a logger not in the database can be registered in the weekly review with a typed code, a confirmed unit and an existing fridge. It is saved only at Import, as one `loggers` row and one undated `logger_assignments` row. Nothing is created from a guessed file name, no date is invented, and known loggers need no per-file setup.
14. **Column validation:** optional `Logger`, `Branch` and `Fridge` columns are checked against the resolved mapping and a disagreement is reported as `needs_attention` with nothing written. A `Time`/`Temp`-only file stays valid, and the columns never resolve an ambiguous file.
15. **Weekly fridge-first dashboard:** the dashboard opens on the latest week containing readings, a week selector switches weeks, and all readings in the selected week are analysed. There is one card per physical fridge with its result, maximum recorded temperature, counts of excursions (sustained and isolated spikes), warming runs, gaps and invalid readings, and coverage. Analysis stays per logger and fridge series, and a fridge detail shows each series on its own, including loggers that moved. No trend joins unrelated series.
16. **Retrospective honesty:** every excursion strictly above 5 C stays visible after recovery, with a conservative duration. "No excursion observed" is reported only with coverage of at least `MIN_COVERAGE`, otherwise the result is "insufficient data", and unobserved periods are listed and never called safe. There is no `FRESH_MAX_MIN`, no `now` or clock input, and no real-time status such as `active_excursion` or `stale` anywhere in the API or UI.
17. **Integrity:** the same logger and time under a different fridge is a reported conflict even with an identical value, never inserted or overwritten. Registering a move rewrites no stored reading.
18. `docker compose exec backend pytest` and the frontend tests pass with a non-zero collected count, `/health` still returns 200, and Phase 2 code and the schema are unchanged.
